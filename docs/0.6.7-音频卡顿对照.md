# 0.6.7 音频与卡顿对照

## 结论

音乐／环境循环音频通路是已测到的显著性能拖累因素，不再只是猜测。但尚未证明它是用户整页无响应的唯一原因，也未定位到具体底层调用。正式版本未修改，不能宣称已修复。

## 方法

独立 Chrome、1280×800、DPR 1、Intel Arc / ANGLE D3D11。固定第 17 关四台机器人位置与玩家位置，每阶段验证实际扫描数为 4、警报点光源数为 4，保留公共界面／瞄准／紧张状态与边缘效果更新。无线电和移动被隔离，不是完整自然游玩验收。

在游戏初始化后通过真实鼠标点击解锁 WebAudio，等待测试开始。所有阶段的 AudioContext 均确认为 running。按 off→all→off→music→off→cues→off→all 交错进行；每阶段重置紧张音频，先停止所有播放器，再按分组启动。off 是彻底停止播放，不是音量设零；阶段末播放器数量为 0，PCM 为零。

每阶段 120 帧，前 40 帧单列为过渡期，后 80 帧统计。PCM 为阶段末单个 analyser 窗口，不是全程录音；其作用是验证循环音频实际有输出，而非仅播放标记。

## 测量

| 配置 | 帧间隔中位数 | 公共更新中位耗时 | 播放器 / 阶段末 PCM |
|---|---:|---:|---|
| 全停，第 1 次 | 24.8ms | 0.7ms | 0 / 零输出 |
| 原有全部音频，第 1 次 | 39.3ms | 14.5ms | 5 / RMS -21.97dBFS |
| 全停，第 2 次 | 23.1ms | 0.7ms | 0 / 零输出 |
| 仅循环音乐＋环境声，停止检测／心跳提示 | 36.5ms | 13.5ms | 5 / RMS -21.20dBFS |
| 全停，第 3 次 | 25.0ms | 0.6ms | 0 / 零输出 |
| 仅检测／心跳提示，停止循环音乐与环境声 | 33.4ms | 0.9ms | 阶段末处于提示间隙，0 / 零输出 |
| 全停，第 4 次 | 25.0ms | 0.7ms | 0 / 零输出 |
| 原有全部音频，第 2 次 | 40.8ms | 15.0ms | 5 / RMS -19.76dBFS |

全停约 40–43 FPS，原有全部音频约 25 FPS；这些是中位帧间隔倒数，不是整段平均 FPS。只启用循环音频仍明显变慢，足以把循环音频通路列为重点；不能把仅提示组的单次零 PCM 读数当作全阶段无声音，也不能据此认定心跳完全没有性能问题。

第二次全部音频的稳定期最大帧间隔 119.5ms，过渡期最大 127.1ms。所有阶段完成、错误列表为空；无整页无响应复现。

## 源码关联与待验证

当前 unlock 同时启动环境声、平静音乐以及 suspicion/chase/recovery 三层，共五条循环音频；低音量／零混合权重不等于停止播放。mix_state 和 mix_tension 每帧写入多个播放器音量及暂停状态。上述结构与实测一致，但还需对照验证到底是多流播放、每帧参数更新、暂停属性重复赋值或其他音频后端开销，不能直接声称“OGG 解码已定位”。

修复方向：优先检查每帧重复音频状态写入、无用音乐层持续播放；保留背景音乐、心跳、检测提示及已有脚步／按钮／装备音效。修复后用同组 A/B 和真实移动追捕、音频连续性／暂停／独立音量回归。

本轮比此前多扫描测试增加了实际用户手势解锁和 PCM 验证；此前音频上下文状态未验证，跨轮绝对 FPS 不应直接比较。
