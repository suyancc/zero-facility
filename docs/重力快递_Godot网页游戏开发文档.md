# 《重力快递》Godot 网页游戏开发文档

**文档版本：** 1.0  
**编写日期：** 2026-10-03  
**项目代号：** Gravity Courier  
**交付形态：** 桌面浏览器可玩的风格化 3D 小游戏＋完整 Godot 工程＋开发实录素材  
**开发方式：** 人类负责方向、授权与试玩；AI 经 EasyAI MCP 操作项目、执行构建和检查；Godot 负责游戏；必要时用 Blender MCP 整理模型。

> 本文是一份可直接分阶段执行的开发规格，不代表游戏或兼容性已经完成验证。采用的 Godot 具体版本、测试设备、MCP 工具能力和素材清单，必须在项目开始时登记。所有性能数字是项目目标，不是现有测试结果。

## 0. 决策摘要

### 0.1 游戏定位

一句话：**玩家不能直接搬快递，只能改变运输台上的重力方向，把包裹送进接收舱。**

- 风格：精致、明快的科幻微缩实验室；不是写实开放世界。
- 视角：固定三分之四俯视，透视较弱；不做自由第三人称摄像机。
- 玩法：观察路线、短促施力、反向减速、触发机关、完成投递。
- 单关时长目标：首次游玩约 30–120 秒；三关体验约 5–10 分钟，最终以试玩调整。
- 情绪：小心翼翼、差一点成功、失误后迅速重来、送达时清晰愉悦。
- 视频看点：方块原型逐步变成科幻场景；同一套规则遇到易碎物和双包裹后产生新挑战。

### 0.2 已确定的技术方向

| 项目 | 决策 |
|---|---|
| 引擎 | Godot 4.x 稳定版，项目启动时锁定具体版本 |
| 脚本 | GDScript，不使用 C# 作为网页交付基础 |
| 渲染 | Compatibility，从第一个场景开始使用 |
| 首发设备 | 桌面浏览器＋键盘，Windows Chrome/Edge 为首轮测试对象 |
| 次级验证 | macOS Chrome/Safari；以实测结果列支持范围 |
| 网页导出 | 首版优先单线程；不依赖多线程才能运行 |
| 物理 | 固定场景碰撞＋可控制的重力向量＋RigidBody3D 包裹 |
| 角色 | 非必需；可爱快递箱为主要视觉主体，机器人作为后续装饰 |
| 美术来源 | 一套主风格素材＋少量原创调整；保留许可清单 |
| 开发顺序 | 最小网页构建 → 灰盒玩法 → 视觉切片 → 三关 → 浏览器优化 |

### 0.3 一个关键取舍：不真的旋转全部物理场景

首版“改变重力”通过改变包裹所受力的方向实现，**平台、护栏、接收舱的碰撞体保持静止**。玩家看到的主要反馈是包裹运动、重力箭头、方向灯和小幅镜头反馈。

这样避免不断旋转大量碰撞体导致穿透、卡顿、抖动和摄像机眩晕。

- 对外描述为“改变重力方向”，不要把首版宣传成“整个房间真实翻转”。
- 不允许把可见平台倾斜很大角度、碰撞平台却不动，以免形成视觉和碰撞错位。
- 整个房间 90° 翻转属于后续独立实验，不纳入首版。

## 1. 项目目标与范围

### 1.1 三个核心目标

1. **能玩：** 控制能理解、减速可预判、失败原因清楚，玩家愿意再试一次。
2. **好看：** 在真实网页构建中形成统一的镜头、配色、材质、灯光与反馈。
3. **能拍：** 开发过程存在明确里程碑，方便展示 MCP 的读取、修改、构建、验证能力。

优先级：可玩性与稳定性 > 视觉一致性 > 内容数量 > 非必要特效。

### 1.2 首版必须完成

- 标题／开始界面；必要的首次加载提示。
- 三个小关卡，支持按顺序游玩、重试、返回关卡选择。
- 键盘方向输入、重力回中、反向减速。
- 普通包裹、易碎包裹、压板与门、接收舱、掉落区。
- 成功与失败状态，计时和失败原因。
- 音量设置、静音、减弱镜头效果选项。
- 可检查的 Web 导出和部署文件。
- 操作说明、素材许可、已知限制及浏览器测试记录。

### 1.3 首版明确不做

联机、登录、支付、云存档、全球排行榜、内购、角色换装、开放世界、随机生成完整地图、复杂 NPC AI、移动端正式适配、真实液体、布料、复杂破碎、多重重力区域。

允许本地保存已解锁关卡、最佳成绩和设置；读取失败时应能继续游玩。

### 1.4 首版成功标准

- 初次接触者不看长教程，也能在 30 秒内理解基本控制；该目标通过观察试玩验证。
- 三关能在浏览器中从头到尾完成。
- 反复重开不出现重复实例、状态残留、镜头漂移。
- 至少一个录屏镜头无需解释即可看出玩法特色。
- 原型到最终版是同一 Godot 项目的渐进迭代，不重写成另一技术栈。

## 2. 核心玩法规格

### 2.1 循环

观察目的地 → 施加重力方向 → 包裹移动 → 松手／反向输入修正 → 触发机关 → 满足投递条件 → 反馈、计分、进入下一关。

失败后必须快速重试，不强制重看开场。

### 2.2 操作

| 输入 | 行为 |
|---|---|
| W / ↑ | 沿画面对应的“远侧”方向施力 |
| S / ↓ | 沿相反方向施力 |
| A / ←、D / → | 左右施力 |
| 松开方向键 | 重力方向平滑回中，水平速度逐渐衰减，但不瞬间归零 |
| R | 重开当前关；可在失败状态直接使用 |
| Esc | 暂停／继续；浏览器全屏退出可能优先处理 Esc，需实测 |
| M | 静音切换 |

- WASD 和方向键等价；界面显示最简单的一套，不堆满按键。
- 斜向输入归一化，不能因为同时按两个方向而更快。
- 浏览器失焦或页面切到后台时暂停并清除输入；恢复后等待玩家明确继续。
- 游戏画布获得焦点后再处理按键，不拦截整个网页的常规输入。
- 首版不设计“每帧切换重力方向”的复杂组合技。

### 2.3 包裹类型

**普通包裹**

- 主要教学对象；质量和尺寸固定。
- 具有明显正面、角部和可识别色彩。
- 允许自然翻滚，不要求正面朝上才能送达。

**易碎包裹**

- 初版只引入一个差异：超过阈值的有效碰撞会破损。
- 以冲击强度和清晰反馈引导减速，而不是依靠随机判定。
- “蛋糕不能翻面”可作为后续加料，不和易碎规则在第一版同时引入。

**压板用包裹**

- 与普通包裹共用控制机制；外观和接收目标明确区分。
- 第三关两个包裹同时受全局重力，不能点击单独遥控。
- 通过护栏、凹槽和停靠区让一个包裹停住，玩家再移动另一个。

### 2.4 投递规则

仅满足以下全部条件时成功：

1. 是本关目标包裹，类型或颜色匹配。
2. 未破损、未掉落、游戏仍处于 PLAYING。
3. 包裹主要碰撞盒的底部角点位于接收舱内部的判定范围；不能只靠中心点碰到边缘。
4. 水平速度和角速度低于阈值。
5. 连续稳定停留达到设定时长，例如初始调参值 0.5 秒。

Area3D 只负责发现候选包裹。最终检测由接收舱脚本完成，目标容差应可配置。

成功后停止关卡输入，把包裹平滑固定在投递展示位置，播放接收舱反馈，且只触发一次成功事件。

### 2.5 失败规则

- 包裹进入 KillZone 或低于高度阈值。
- 易碎包裹达到损伤条件。
- 物理状态非正常，例如检测到无效数值时中止本关并给出可重开提示，记录诊断。
- 无解状态提供重试，不强制倒计时判死；例如目标包裹被推入不可恢复角落。

第一关不设置强制时间限制。首版计时用于反馈，不制造过早的焦虑。

### 2.6 评分

每关保存：完成状态、有效游玩时间、重试次数、易碎物碰撞记录。

- MVP 只显示“送达”和用时。
- 三星／评级等到关卡经过试玩后再设阈值，不能在开发前随意承诺难度。
- 不把页面加载时间、暂停时间计入成绩。

## 3. 三关设计

### 3.1 第一关：首次投递

**目的：** 学会施力、回中和反向减速。

- 运输台约 10 × 8 个世界单位，仅作为起始比例。
- 大部分边界有护栏，只有一个有明显警示的小缺口。
- 起点到终点经过一段直线和一次转向。
- 接收舱较宽，降低首次失败惩罚。
- 首次显示简短提示：“方向键改变重力，反向按可减速”。
- 玩家第一次实际输入后淡出操作提示，但保留暂停菜单中的帮助。

**验收：** 新用户无需口头指导能完成；最短路径不是按住一个方向到底。

### 3.2 第二关：易碎件请轻放

**目的：** 学会预判速度，不只依赖护栏挡住。

- 单个易碎包裹。
- 一个缓冲区域、一处较窄弯道和一个接收舱。
- 危险墙角使用同一色彩和形状语言。
- 碰撞出现明显闪光、短音效和包裹状态变化。
- 阈值附近有宽容区，不能轻碰就失败。

**验收：** 失败时玩家知道撞到了什么；不同帧率下不会出现明显不同的损坏概率。

### 3.3 第三关：双件联动

**目的：** 利用同一重力下的两个物体完成简单空间解谜。

- 一个压板包裹，一个待投递包裹。
- 压板触发后，隔离门打开；首版推荐门锁存，避免必须完美同时保持两个物体。
- 压板旁有停靠凹槽，阻止包裹滑走。
- 门打开后目标路线变得可达。
- 若之后增加“离开压板门会关”，必须有夹物防护，不让门直接穿过包裹。

**验收：** 首次观察能识别压板和门的关联；不存在只能靠高速碰撞穿模完成的路线。

### 3.4 关卡草图示意

```text
┌──────────────────────────┐
│ 起点A      护栏／安全区    │
│   □ ────→ ┌─────┐        │
│           │压板 ●│──门──┐ │
│           └─────┘      │ │
│ 起点B □ ─────────────→ ◎ │
│      警示缺口       接收舱│
└──────────────────────────┘
```

这是拓扑关系，不是最终尺寸图。灰盒试玩后再定尺寸和路径。

## 4. 视觉方向与验收

### 4.1 美术原则

关键词：**微缩、圆角、干净、柔和科幻、可读、轻松**。

- 主体是一个有边框的运输台，不是一座大型空间站。
- 地面图案和道具强调路线，背景不争夺注意力。
- 包裹轮廓有辨识度，在缩小的视频画面中仍能追踪。
- 有明确材质层次：哑光地面、稍亮的金属边框、柔和发光指示。
- 字体、图标、音效和模型许可一并管理。

### 4.2 初始色彩表

| 角色 | 建议色 | 用途 |
|---|---|---|
| 背景 | 深蓝 `#101A2E` | 太空或简洁渐变 |
| 主结构 | 灰白 `#DCE5EE` | 墙体与运输台 |
| 玩家关注物 | 橙 `#FF9A3D` | 普通包裹 |
| 正向目标 | 青 `#55DDD0` | 接收舱、连通指示 |
| 危险 | 珊瑚红 `#F16C78` | 掉落边缘、破损提示 |
| 机关辅助 | 紫 `#A38BFA` | 压板、线路 |

颜色必须搭配形状／图标，不能只靠红绿差异表达状态。

### 4.3 镜头

- Camera3D 使用近似等距视角，可先尝试正交，若纵深不清楚再改较小透视角。
- 镜头保持整个可玩区域可见，不跟随包裹猛转。
- 重力反馈不应导致真实镜头大角度滚转。
- 屏幕震动短、弱、有开关；失败不连续闪烁。
- 16:9 作为录制主构图，兼容窗口缩放和较窄比例，UI 不盖住接收舱。

### 4.4 网页可实现的灯光和材质

- 先使用一个主要方向光／简单环境照明，限制实时投影光源数量。
- 使用简单 PBR 材质或可验证的轻量自定义 shader。
- 发光外观不意味着必须有屏幕 Bloom；网页 Compatibility 下应逐项验证效果支持。
- 不依赖体积雾、屏幕空间反射或桌面专属效果才能成立。
- 需要烘焙照明时先对小场景验证浏览器效果、导出结果和包体，不直接引入全场景复杂烘焙流程。

### 4.5 视觉切片必须先于大量关卡制作

只完成一个小片段：最终地面、包裹、接收舱、一段墙体、UI、音效和成功反馈。

验收条件：

- 截图来自网页运行，不使用离线渲染冒充实际游戏。
- 缩到 640 × 360 仍能分辨包裹、目标、危险区域。
- 关闭非必要特效后仍有明确构图。
- 视觉模型和碰撞边界基本一致，不存在悬空或穿墙假象。
- 得到用户确认后再进行第二、第三关的最终美术。

## 5. 素材策略与 Blender 工作

### 5.1 主素材候选

| 来源 | 推荐内容 | 许可／注意事项 |
|---|---|---|
| Quaternius Modular Sci-Fi Megakit | 地板、墙、门、实验室组件 | 官方页面标注 CC0；免费部分与完整／引擎源码档位分开核对 |
| Quaternius Sci-Fi Essentials Kit | 机器人、箱体、屏幕、道具 | 官方页面标注 CC0；先核对免费包真实内容 |
| Kenney Platformer Kit | 若改为玩具／天空岛路线时使用 | CC0；不与科幻主套装随意混用 |
| Poly Haven | 少量环境、材质、必要模型 | 资产 CC0；注意复杂度、贴图大小和风格 |

不要同时引入多个主风格。若免费科幻包不满足需求，先用简单原创几何体补齐，不默认购买付费资源。

### 5.2 下载前检查

- 是否可商业使用、录屏展示、修改和随游戏分发。
- 是否允许随公开项目分发原始文件。
- 是否有署名、相同方式共享或非商业限制。
- 角色、动画、音效、字体分别核验，不能用模型许可代替整个素材包许可。
- 官方预览图不等于可再分发的素材；不直接拿预览图当游戏资源。
- 保留 LICENSE、来源 URL、下载日期、文件哈希和具体使用文件。

### 5.3 导入标准

- 优先 GLB/glTF；不依赖每次打开 Godot 都要调用 Blender 才能导入。
- 约定 1 Godot 单位对应 1 米作为资产比例基准；手感参数仍以游戏为准。
- Godot 世界向上为 +Y；资产导入后统一朝向、原点、缩放。
- 对动态箱体优先使用简单 BoxShape3D，不使用动态凹三角网格碰撞。
- 环境碰撞尽量由简单盒体／凸体组成；复杂静态形状需要单独评估。
- 初始纹理使用 512–1024 分辨率，关键近景按需提高，不默认 4K。
- 合并不必要材质，限制透明叠层和大量独立小网格。
- 不直接修改导入场景内部生成节点；用包装场景和继承／实例引用管理游戏逻辑。

### 5.4 Blender MCP 的具体用途

只用于明确的小任务：调整尺寸、应用变换、减面、整理材质、添加简单表情、导出 GLB、修复朝向。

首版不要求 AI 从零建造复杂人形角色，也不把实时布料、毛发、破碎作为视觉卖点。

## 7. 重力与物理实现

### 7.1 控制坐标

- 游戏平台处于 XZ 平面。
- 向上为 +Y，默认重力向下。
- 根据固定摄像机，把输入映射到平台平面上的前／右方向；相机向量投影到 XZ 后归一化。
- 输入方向与屏幕视觉一致，W 不能出现不直观的斜反方向。

### 7.2 重力模型

初始方案：重力总量基本不变，最大倾斜角有限。

```text
u = 归一化后的二维输入
θ = 最大倾斜角 × min(输入长度, 1)
h = 平台平面上的输入方向
目标重力 = g × (sin(θ) × h - cos(θ) × UP)
```

零输入时目标重力为向下；当前重力方向使用与时间相关的平滑方式趋近目标，例如指数平滑，避免不同帧率改变手感。

起始调参范围，仅供实验：

| 参数 | 初始范围 |
|---|---|
| 物理频率 | 60 Hz |
| 重力强度 | 约 9.8–14 世界单位/秒² |
| 最大倾角 | 约 15°–25° |
| 方向响应时间 | 约 0.12–0.25 秒 |
| 接收稳定时间 | 约 0.4–0.7 秒 |
| 正常最高水平速度 | 根据关卡尺度调节，初试 3–5 单位/秒 |

这些值不能脱离箱体尺寸、摩擦、平台长度单独评价。

### 7.3 实现约束

- 首版只让指定 parcel 分组中的物体受到游戏重力，不修改全局世界方向以免意外影响装饰。
- 若使用自定义重力力，包裹关闭默认重力贡献，避免双重重力。
- 推荐在物理更新／积分回调内施加持续力；不要在渲染帧直接修改 RigidBody3D 的 transform 来移动它。
- 持续力按 F = m × a 计算；使用持续力 API 时不要再随意乘一次 delta。若采用冲量，则是不同时间积分方式，不能混用。
- `custom_integrator`、默认阻尼及自定义阻尼只能选择经过验证的一套组合，避免隐式重复计算。
- 不假定把节点旋转了就正确修改了物理参考系。
- 最初保持动态物体少量，先调好一个，再增加第二个。

### 7.4 摩擦、减速与翻滚

- 保留真实速度和惯性，但松手不能无限滑行。
- 先调整 PhysicsMaterial 的摩擦和反弹，再补必要的温和水平阻尼。
- 默认弹性低，不能像弹珠一样连续蹦跳。
- 反向重力应能够主动减速；不要用瞬间清零速度冒充刹车。
- CCD 可作为高速穿透防护选项，但不能替代合理速度、墙厚和碰撞体。
- 是否限制部分旋转轴以提升可控性，作为独立实验记录；最终选择后统一规则，不针对不同失败临时作弊。

### 7.5 易碎判定

不使用“发生碰撞就扣血”。

初版可以基于接触前后的相对法向速度等物理信息近似估计冲击；该近似必须标明并测试。若锁定的 Godot 版本和物理后端能可靠提供接触冲量，再评估使用。

- 设置最低有效阈值与明显破损阈值。
- 同一次持续接触加入冷却／去重，避免一帧反复扣损。
- 地面静止接触不应持续造成破损。
- 护栏、地面、装饰层分组明确。
- 30/60 FPS 图形帧率下都做碰撞回归；物理频率保持一致。

### 7.6 重开与恢复

最稳妥的首版策略：销毁并重新实例化当前关卡，保持外层 UI／设置服务。

重开需重置：包裹实例、速度、角速度、重力平滑状态、机关、计时、成功失败标志、音效循环、临时粒子和输入。

禁止把旧包裹留在场景里隐藏起来，再叠加新实例。

## 8. 状态机与边界

```text
BOOT → MENU → LOADING_LEVEL → READY → PLAYING
                                    ↓     ↓
                                  PAUSED  WON / LOST
                                    ↓       ↓
                                 PLAYING  RETRY / NEXT / MENU
```

- READY：显示关卡，等待首次输入或开始按钮，音频可在用户手势后解锁。
- PLAYING：允许输入、物理推进、计时。
- PAUSED：关卡停止推进，UI 仍响应；配置正确的 process_mode。
- WON/LOST：输入锁定，同帧重复事件不会二次结算。
- LOADING_LEVEL：禁止重复点击生成多个关卡。
- 标签页重新激活：不自动补算长时间物理，不突然飞出包裹。

明确成功与失败同帧的裁决规则：若目标包裹已破损／掉落，不接受投递成功；结果一经提交不再反转。

## 9. UI、声音与第一次体验

### 9.1 最少页面

1. 标题：游戏名、开始、操作、设置、制作信息。
2. 游戏 HUD：关卡名、重力方向、暂停、必要状态。
3. 成功：送达反馈、用时、下一关、重试。
4. 失败：具体原因、明显的重试按钮。
5. 设置：主音量、静音、减弱镜头效果。

不把软件购买、群二维码塞在游戏过程中。若放开发工具介绍，放在制作信息或体验结束页，明确是开发者自己的工具。

### 9.2 音频

- 浏览器通常需要用户交互后才能正常启动音频，首屏按开始时初始化。
- 音乐可暂不加入，先完成碰撞、机关、成功、失败四类反馈。
- 同一碰撞事件限制音效并发，防止物理抖动制造噪声。
- 素材许可独立记录；不使用来源不明的热门游戏音效。

### 9.3 本地保存

保存路径采用 Godot 的 `user://` 机制并做 Web 实测。

- 仅保存设置、解锁进度和成绩。
- 存储不可用、隐私模式或数据损坏时回到默认值，不阻断游玩。
- 提供重置进度并要求确认。
- 不承诺跨浏览器或清缓存后仍保留。

## 10. 性能预算与网页部署

### 10.1 暂定预算

| 指标 | 第一轮目标 |
|---|---|
| 标准测试设备 | 项目开始时登记 CPU/GPU/内存/系统/浏览器 |
| 图形帧率 | 标准设备 1080p 目标 60 FPS；低配提供可接受降级 |
| 动态刚体 | 首版同时约 1–4 个，装饰尽量静态 |
| draw call | 初期目标控制在约 150 以内，结合实际 profiler 判断 |
| 场景三角形 | 初期可见总量目标约 15 万以内，非硬性引擎上限 |
| 下载包体 | 初期目标总下载约 30 MB 内，需分别记录未压缩和实际传输大小 |
| 画质设置 | 至少提供降低阴影／效果的方式 |
| 重开稳定性 | 连续 20 次重试无明显资源累积和状态异常 |

不能只靠面数判断性能；阴影、材质切换、透明叠加和脚本也必须检查。若预算不合理，要记录原因和调整，不假报达标。

### 10.2 导出原则

- 安装与引擎完全匹配的导出模板。
- 导出预设命名为 `Web`，使用 Compatibility。
- 首版单线程；若后续开启线程，必须专门验证跨源隔离与托管头配置。
- Web 构建不是单一 HTML：需要同时部署引擎 WASM、资源包、JS 等所有导出文件。
- 从 HTTP／HTTPS 静态服务器访问，不使用双击 `file://` 作为正式验证方式。
- 线上使用 HTTPS，WASM MIME、压缩和缓存策略按导出产物配置并验证。
- 没有需要跨域的外部运行时资源时，尽量全部同源托管。
- 不在公开游戏资源中包含 MCP URL、user_key 或任何后台密钥。

### 10.3 示例命令

以下使用 `godot` 作为占位命令。Windows 可能要指定实际 Godot console 可执行文件，启动阶段先确定。

```bash
# 检查版本
godot --version

# 导入资源并退出：能发现部分导入与脚本错误，不等于完成运行测试
godot --headless --path . --editor --import

# 运行项目测试脚本（该脚本需实际实现并返回正确退出码）
godot --headless --path . --script res://tests/run_tests.gd

# Web 正式导出：提前创建目标目录并配置 Web 预设
godot --headless --path . --export-release "Web" exports/web/index.html
```

静态预览服务应使用能够持续运行的进程工具管理；只绑定所需网络范围。远程预览若要求 `0.0.0.0`，需检查暴露范围且不要把私有源文件目录一起开放。

### 10.4 兼容性声明

- Windows Chrome/Edge：第一轮必测。
- macOS Chrome/Safari：正式声称支持前必测。
- Firefox：建议补测。
- 手机和平板：首版不承诺正式支持；页面说明需键盘，不让用户误以为触控已经可用。
- 嵌入 iframe：验证键盘焦点、全屏和音频限制；无法稳定运行时提供独立页面。

## 11. MCP 开发规程

### 11.1 开始前必须确认

- 开发机器是 Windows 还是 macOS。
- 新项目绝对路径；必须使用新目录，不默认修改 EasyAI 已发布源码。
- Godot 是否安装、实际版本和命令路径。
- Web 导出模板是否就绪。
- 当前 MCP 的可用工具：文件、执行、日志、长进程、截图／浏览器／编辑器操作。
- Blender MCP 是否必要、是否可用；缺少时不能阻塞灰盒开发。
- 素材预算为免费优先；任何付费下载先征得同意。

### 11.2 每个阶段的工作循环

1. 检查项目状态和现有实现。
2. 提出本阶段计划与验收条件。
3. 只实现一个可验证的小目标。
4. 运行针对性检查，观察完整输出和退出码。
5. 启动游戏／导出 Web，做视觉和交互验证。
6. 检查差异，更新阶段记录。
7. 展示结果，等待必要的美术或玩法确认。

如果没有截图和交互工具，应明确请用户试玩并提供截图，而不是凭“进程启动成功”声称画面正确。

### 11.3 权限与安全

- MCP 只绑定演示项目，录制时不打开私人目录。
- 不把真实凭据放进命令行、日志、Git 或视频。
- 不自动提交、推送、发布网站或购买资源；执行前按用户授权确认。
- 不无故删除已有文件；生成目录清理应限定到本项目可再生输出。
- 不为演示修改全局系统设置或结束其他用户进程。
- 数据收集只做必要的匿名产品指标，首版游戏可以完全不接统计。

## 12. 里程碑与验收门槛

### M0：环境与最小 Web 构建

**输出：** 空项目、基础场景、可在浏览器显示和响应按钮的 Web 版本。

**验收：** 版本与模板匹配；Compatibility 生效；从服务器打开无阻断错误；基本输入和用户手势后的音效验证完成。

**禁止提前做：** 导入整套大型素材、复杂 UI 或多关卡。

### M1：第一关灰盒可玩

**输出：** 一个包裹、静态平台、护栏、目标、掉落区、重试、基础 HUD。

**验收：** 能完整送达；反向输入可减速；斜向不加速；20 次重开无状态残留；有浏览器试玩记录。

**决策门槛：** 若手感不好，继续 M1，不靠美术掩盖。

### M2：视觉切片

**输出：** 一小块正式风格场景、最终包裹、接收舱、反馈和配色。

**验收：** 用户认可网页实际截图；素材授权记录齐全；基础性能无明显退化。

**决策门槛：** 本阶段需要人工美术确认，未确认不批量铺设三关。

### M3：第二、第三关

**输出：** 易碎件、压板和门、双包裹关卡。

**验收：** 每关能合法通关，规则可理解；成功失败只结算一次；第二关碰撞判定稳定；第三关没有夹物穿模捷径。

### M4：产品化与 Web 优化

**输出：** 菜单、关卡选择、设置、成绩、本地保存、加载与错误提示。

**验收：** 完整浏览器测试矩阵、实际包体和帧率报告、已知问题清单、发布候选构建。

### M5：录制与发布准备

**输出：** 干净演示账号／项目、录制计划、完整开发证据、游戏体验入口准备。

**验收：** 无秘密信息出镜；视频中的效果来自实际游戏；素材署名与软件商业关系说明完整；正式发布由用户确认。

时间安排不预先保证。先完成 M0/M1，再按实测复杂度估算后续工期。

## 13. 测试计划

### 13.1 自动／脚本测试

无图形测试能验证逻辑，但不能证明画面和浏览器交互正确。

| 编号 | 项目 | 预期 |
|---|---|---|
| T01 | 输入向量归一化 | 斜向力度不超过单轴上限 |
| T02 | 重力回中与平滑 | 稳定、有限值，不出现 NaN |
| T03 | 状态转移 | WON/LOST 不二次结算 |
| T04 | 计时暂停 | 暂停不累计成绩 |
| T05 | 投递稳定时间 | 短暂擦边不成功 |
| T06 | 包裹目标匹配 | 错误包裹不触发投递 |
| T07 | 压板与门 | 正确触发，重试后复原 |
| T08 | 易碎碰撞冷却 | 同一接触不重复扣损 |
| T09 | 存档损坏 | 回退默认，不阻塞启动 |
| T10 | 关卡资源完整 | 所有引用路径可加载 |

脚本测试允许使用自定义 SceneTree 测试入口或项目选定框架。引入第三方测试框架需记录版本和许可证，不为测试安装大量无关依赖。

### 13.2 人工与浏览器测试

- 开始按钮、键盘焦点、方向键页面滚动冲突。
- 30/60 FPS 条件下的手感与失败判定。
- 按住方向时切后台、恢复、暂停、重开。
- 连续快速按 R、下一关、返回菜单。
- 包裹卡在墙角、接收舱边缘、门附近。
- 同帧掉落／碰撞与投递事件。
- 静音、首次音频、关闭音效后再次进入关卡。
- 窗口尺寸变化、全屏、不同显示缩放。
- 清空本地存储、隐私模式、刷新页面。
- 慢网络首次加载、缓存后二次加载。
- 浏览器控制台无阻断错误。

### 13.3 缺陷分级

- P0：泄露凭据、无法启动、严重数据／文件风险。
- P1：无法通关、频繁穿模、输入失控、重开失效。
- P2：偶发物理抖动、明显帧率问题、UI 遮挡。
- P3：装饰细节、轻微文字或音效问题。

公开试玩前必须清零 P0/P1；P2 要么修复，要么明确限制并获得确认。

| 开场 10–15 秒 | 成品关卡中的险些失败与最终送达 |
| 挑战说明 | 不能直接搬箱子，只能控制重力；说明工具是自己开发的 |
| 第一阶段 | MCP 建项目，方块开始运动，第一次失败 |
| 第二阶段 | 修改减速／碰撞／重试，展示真实问题如何解决 |
| 第三阶段 | 免费素材导入，灰盒与精修画面对比 |
| 加料挑战 | 易碎快递或双包裹机关 |
| 最后试玩 | 实际网页运行，说明完成度与限制 |
| 结尾 | 游戏体验与开发教程分开提供，不强制进群才能玩 |

### 14.3 录制规则

- 完整开发录屏另存，成片可剪辑和加速，并明确时间压缩。
- 保留真实错误，但不要故意制造假失败误导观众。
- 人工建模、手改代码、素材使用如实标注。
- 每个阶段录一段相同视角素材，便于前后对比。
- 开发工具证据用短镜头：调用记录、代码差异、构建输出、实际效果。
- 不展示完整 MCP capability URL、授权密钥、账号 Cookie 或私人邮箱。
- 录制完成后按实际工具机制撤销演示连接；确保不会影响私人项目。
- 不承诺具体模型身份、无限使用或未经验证的性能。

### 14.4 关键录制素材清单

- 第一张灰盒截图。
- 第一版成功与失败各一段。
- 一次真实物理问题及修复前后。
- 正式素材替换前后固定镜头。
- 三关各一段完整试玩。
- 浏览器部署页面与实际加载。
- MCP 修改与测试的证据片段。
- 素材作者与许可名单。

## 15. 可直接交给 AI 的分阶段任务指令

### 指令 A：环境核对与 M0

> 我们开发《重力快递》，使用 Godot 原生项目并最终导出 Web。先只做环境核对和最小网页构建：确认新项目路径、Godot 具体版本、Web 模板和当前 MCP 工具能力。使用 GDScript 与 Compatibility，优先单线程 Web。不要修改其他项目，不导入大型素材，不发布线上网站。建一个简单场景和开始按钮，实际导出并在浏览器验证输入。报告运行过的检查以及尚未验证的部分。

### 指令 B：M1 灰盒玩法

> 在现有 Godot 工程实现第一关灰盒。场景碰撞固定，通过受控重力向量推动 RigidBody3D 包裹；支持方向键／WASD、回中、反向减速、掉落、稳定投递、失败重开和暂停。把视觉节点与碰撞逻辑分开，调参集中管理。先实现一关，不加入复杂美术。检查斜向速度、边缘投递、失焦和连续重开，提供网页试玩结果。

### 指令 C：M2 视觉切片

> 保留已验收的玩法，只制作一个最终视觉切片。使用统一的科幻主素材，下载前核对免费范围和许可证，维护素材清单。橙色包裹、青色目标、深蓝背景、灰白结构；固定三分之四镜头。不得依赖桌面专属渲染效果，不大幅改变物理尺寸。输出网页实际截图和灰盒对照，等我确认再扩关卡。

### 指令 D：M3 玩法扩展

> 在已验收版本上加入第二关易碎件和第三关双包裹机关。一次完成一个机制并验证，不重写整个项目。损伤不能按每帧接触反复触发；双包裹同受重力，机关规则清晰。每个机制都附回归测试和试玩记录，确认不破坏第一关。

### 指令 E：发布候选与录制

> 完成设置、失败提示、关卡选择和本地存档容错。导出网页候选版本，按测试矩阵记录浏览器、设备、包体和帧率。整理 README、许可证、已知问题及录制镜头。不要自动提交、推送或公开部署；先报告候选版本状态，等待授权。

## 16. 风险与应对

| 风险 | 应对 |
|---|---|
| 素材预览漂亮，免费部分不足 | 下载前核对文件，先小场景验证 |
| 换成 Godot 后仍然画面普通 | 强制 M2 视觉确认，不靠引擎名称保证效果 |
| 物理玩法难控 | 限制速度和倾角，先调一个包裹；必要时记录并评估简化物理方案 |
| 浏览器与桌面效果不同 | 每个里程碑都导出 Web，不只在编辑器里检查 |
| 模型替换破坏碰撞 | 碰撞体独立，尺寸规范，保留灰盒回归 |
| 页面失焦导致物体飞出 | 自动暂停、清输入、恢复确认 |
| 同时开发太多系统 | 严格阶段门槛，首版不做联机和商业系统 |
| 视频成了枯燥的操作录像 | 以游戏挑战和可见变化串联，配置独立成教程 |
| 观众只想玩、不想用 MCP | 游戏体验与开发教程分别承接，不把进群人数当唯一结果 |
| MCP 能力不足 | 用已验证工具做文件／构建，视觉环节明确请求人工反馈 |

## 18. 启动前需要用户确认的事项

1. 使用 Windows 还是 Mac 开发与录制？
2. 新 Godot 项目保存在哪个目录？
3. 是否接受“固定平台＋改变重力向量”的首版机制？

6. 初版只保证桌面浏览器，移动端后续再评估，是否接受？
7. 游戏是否计划公开源代码？这会影响素材文件的分发检查。

建议默认：先在常用 Windows 机器开发，免费素材，桌面 Web，科幻实验室，先完成 M0/M1；具体路径和版本由用户确认，不擅自选择。
